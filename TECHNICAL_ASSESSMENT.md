# Technical Assessment & Implementation Plan
## Secure Single-Administrator CMS Integration — My-Portfolio-Website

**Repository:** https://github.com/muhindovicent/My-Portfolio-Website  
**Branch inspected:** `main` (single commit: `eb198a8`)  
**Assessment phase:** Discovery & design only — no application code modified.

---

## 1. Executive Summary

The site is a **static, client-side portfolio** built from a Python build script. It currently has **no backend, no database, and no authentication**. All content is hardcoded in `build.py` and rendered into the `dist/` directory, which is published statically (Vercel "Other framework" preset).

To integrate a secure, single-administrator CMS while preserving the public interface, navigation, and animations, the simplest compatible path is a **Git-based headless CMS (Decap CMS / formerly Netlify CMS)** layered on top of the existing static build. Content moves from hardcoded Python literals into YAML/JSON files in the repository; a single admin authenticates via GitHub OAuth and edits content through an `/admin` UI; each commit triggers a rebuild that regenerates `dist/`. No database, no custom auth server, and no changes to the public HTML/CSS/JS are required.

A secondary, fully custom option (lightweight Python/Node admin API + SQLite + session auth) is documented as a fallback if the owner prefers a self-contained, non-Git system.

## 5. Recommended Architecture

### 5.1 Primary Recommendation: Git-Based Headless CMS (Decap CMS)

**Why this is the simplest compatible fit:**
- Preserves the **entire public interface** (HTML/CSS/JS, animations, navigation) unchanged.
- **No database to provision, no backend to host, no custom auth code** — the auth server is GitHub (OAuth), satisfying "secure single-administrator" by restricting admin access to the owner's GitHub account.
- Content lives as **YAML/JSON files in the repository** alongside the code — reviewable, versionable, backup-friendly.
- The existing `build.py` becomes the CMS consumer: it reads YAML/JSON instead of hardcoded literals.
- Deploy remains static hosting on Vercel; a commit to `main` can trigger a rebuild via Vercel or GitHub Actions.

**Data flow:**
```
Admin edits content in /admin UI
    ↓ (GitHub OAuth — single admin account)
Commit pushes content YAML/JSON to repo/main
    ↓ (Vercel deploy hook or GitHub Actions)
build.py runs, reads YAML/JSON, regenerates dist/
    ↓
Static site served; public UI unchanged
```

**Repository layout after integration:**
```
My-Portfolio-Website/
├── build.py                  # Updated: loads content from /content/*.yaml
├── content/
│   ├── config.yaml           # Decap CMS backend/collection config
│   ├── projects.yaml         # project list + case studies
│   ├── credentials.yaml      # recognition items
│   ├── skills.yaml           # skill categories
│   ├── site.yaml             # hero, bio, nav, contact, footer
│   └── admin/
│       └── index.html        # Decap CMS admin entry point (static)
├── dist/                     # regenerated output (unchanged structure)
├── admin/
│   └── config.yml            # Decap CMS configuration
└── README.md
```

**Security properties:**
- Admin authentication delegated to GitHub OAuth (2FA-recommended on the admin account).
- Admin UI is a static `index.html` + Decap CMS JS served from the same origin; no server-side admin endpoints to exploit.
- Content changes go through Pull Request or direct push to `main`; can require PR review for an extra gate.
- No credentials stored in repo; OAuth credentials live in GitHub App/OAuth App settings (or Decap's `auth_endpoint`).

### 5.2 Alternative: Custom Lightweight Admin (if Git-based CMS is unsuitable)

A self-contained option for completeness:
- **Backend:** Python (Flask/FastAPI) or Node (Express), small, single-purpose.
- **Database:** SQLite (single file, zero config) hosted alongside the app or on Render/Railway/Neon (PostgreSQL) if preferred.
- **Auth:** Session-based (`express-session`/`flask-session`), bcrypt passwords, single admin row, CSRF tokens, secure/HttpOnly/SameSite cookies.
- **API:** `GET /api/content/*` (public read), `POST/PUT/DELETE /api/admin/*` (admin write, session-verified).
- **Publish:** Admin saves → API writes to SQLite → triggers build (or serves dynamic pages). Static `dist/` regenerated and redeployed to Vercel.

**Trade-off:** More code, a running server, DB backups, and auth surface to maintain. Recommended only if the owner wants content fully decoupled from Git.

**Decision:** Proceed with **Decap CMS (primary)** for this plan. The custom-admin API/entity/security design below is included in case the owner elects the alternative.

## 6. Admin Module Design

### 6.1 Admin Module Structure (Decap CMS primary)


```yaml
collections:

        label: Global Site Content
        fields:

      - {label: Slug, name: slug, widget: string}
      - {label: Name, name: name, widget: string}
      - {label: Label, name: label, widget: string}

      - {label: Detail, name: detail, widget: text}

  - name: credentials
```

### 6.2 Custom Admin — Database Entities (alternative option)

If the custom-admin path is chosen, the minimum relational schema (SQLite/PostgreSQL):

**`admins`** (single administrator)
- `id` PK, `email` unique, `password_hash`, `created_at`, `last_login_at`

**`sessions`**
- `id` PK, `admin_id` FK, `token` unique, `expires_at`

**`site_settings`** (singleton key/value or JSON)
- `key` PK, `value` (JSON), `updated_at`

**`projects`**
- `id` PK, `slug` unique, `name`, `label`, `summary`, `detail`, `repo_url`, `demo_url`, `image`, `published` boolean, `created_at`, `updated_at`

**`credentials`**
- `id` PK, `title`, `date`, `issuer`, `description`, `image_path`, `created_at`

**`skills`**
- `id` PK, `category`, `item`, `sort_order`

### 6.4 Security Architecture (applies to both options)

**Authentication & Authorization**
- Single administrator only; no self-registration.
- Decap (primary): GitHub OAuth; enforce 2FA on admin GitHub account; restrict OAuth callback to the site's exact domain.
- Custom (alternative): bcrypt (`cost ≥ 12`), session cookies `Secure; HttpOnly; SameSite=Strict; Path=/;`, CSRF double-submit or SameSite protection, session TTL (e.g., 8h absolute, sliding 1h), lockout after N failed attempts.

**Transport & Headers**
- HTTPS only (HSTS, `Strict-Transport-Security`).
- `X-Content-Type-Options: nosniff`, `X-Frame-Options: DENY`, `Content-Security Policy` restrictive (fonts/images/self only; no `unsafe-eval`).
- No secrets in repo; admin OAuth client secret / DB credentials via environment variables or platform secret store (Vercel Env / GitHub Secrets).

**Content Integrity**
- All writes through validated API/admin UI; input sanitization (HTML escaping) to prevent XSS in rendered pages.
- Image uploads (if custom): type/size validation, virus scan optional, store outside web root or on object storage, serve via signed/checked URLs.
- Audit log: record admin actions (who, what, when) to an append-only log table.

## 7. Technical Risks

| Risk | Likelihood | Impact | Mitigation |
|------|------------|--------|------------|
| Build drift: `build.py` changes break public pages | Medium | High | Keep `build.py` output schema identical to current `dist/`; snapshot-test generated HTML against committed `dist/` before cutover. |
| Decap CMS dependency on GitHub / Netlify identity | Low | Medium | Pin Decap CMS version; keep content YAML in repo so it can be consumed by a future custom build without the admin UI. |
| Admin OAuth lockout (single admin, 2FA) | Low | High | Document recovery: GitHub account recovery codes; add a second trusted admin as fallback. |
| Static hosting model mismatch (Vercel no build command) | Medium | Medium | Add a build step: Vercel "Other framework" with build command `python build.py` and output `dist/`, or use GitHub Actions to build and push `dist/`. |
| Image management in CMS | Medium | Low | Decap `image` widget commits images to repo; set a repo size policy and optimize images before commit. |
| Public animations/reveal JS coupled to DOM classes | Low | Low | Do not alter `.reveal`, `.motion-ready`, or `motion.js` selectors; CMS content only changes text/images, not structure. |
| SEO/meta description hardcoded | Low | Low | Move meta description into `site.yaml` so CMS can edit it. |

## 8. Deployment Requirements

### 8.1 Hosting
- **Public site:** Vercel (existing). Change preset to run `python build.py` as the build command with `dist/` as output directory, OR keep static `dist/` and deploy via GitHub Actions.
- **Admin UI:** Same origin, served at `/admin/` (static `index.html` + Decap JS) — no separate hosting needed for Decap option.
- **Custom admin (alternative):** Requires a persistent server (Render, Railway, Fly.io, or a VPS) + managed Postgres (Neon, already referenced in skills) or SQLite on a persistent disk.

### 8.2 Environment Variables / Secrets
- Decap CMS: GitHub OAuth App client ID (client secret only if using server-side flow; Decap typically uses implicit/client-side). Stored in Vercel Environment Variables or GitHub Secrets.
- Custom admin: `SESSION_SECRET`, `DATABASE_URL`, `ADMIN_EMAIL`, `ADMIN_PASSWORD_HASH`, `BASE_URL`.

### 8.3 CI/CD
- Add GitHub Actions workflow: on push to `main`, run `python build.py`, optionally run a HTML diff/test against `dist/`, deploy to Vercel.
- Require PR review for content changes via Decap CMS (GitHub PR workflow) as an optional governance gate.

### 8.4 DNS / Domain
- No change required. Admin lives at `https://<domain>/admin/` on the same domain as the public site (important for OAuth redirect URIs and cookies).

## 9. Implementation Plan (Phases)

### Phase 0 — Freeze & Baseline (no code changes)
- [ ] Commit current `dist/` and `build.py` as baseline.
- [ ] Document current generated HTML structure so the CMS-driven build can reproduce it byte-for-byte.
- [ ] Verify local preview: `python -m http.server 8000 --directory dist`.

### Phase 1 — Externalize Content (build.py refactor)
- [ ] Create `content/` directory with `site.yaml`, `projects.yaml`, `credentials.yaml`, `skills.yaml`.
- [ ] Migrate all hardcoded data from `build.py` into the YAML files (nav, hero, bio, disciplines, projects, case studies, credentials, skills, contact).
- [ ] Update `build.py` to read YAML (`PyYAML` or hand-rolled minimal parser to avoid new deps — prefer stdlib-compatible approach) and generate identical HTML.
- [ ] Add a test: regenerate `dist/` and diff against baseline to confirm zero public-interface change.
- [ ] **Preservation check:** `style.css`, `motion.js`, and all HTML class names/selectors remain untouched; animations and navigation unaffected.

### Phase 2 — Add Admin UI (Decap CMS)
- [ ] Add `admin/index.html` and `admin/config.yml` (Decap CMS).
- [ ] Configure GitHub OAuth backend; restrict to owner account.
- [ ] Deploy admin at `/admin/`; smoke-test login and content edit → commit.
- [ ] Verify build regenerates `dist/` and public site reflects edits.

### Phase 3 — Harden Deployment
- [ ] Configure Vercel build command (`python build.py`) or GitHub Actions deploy workflow.
- [ ] Add environment variables (OAuth client ID, secrets).
- [ ] Enable HTTPS/HSTS and security headers.
- [ ] Add content-change PR review policy (optional).

### Phase 4 — Handoff
- [ ] Admin user guide: how to log in, edit projects/credentials/site settings, publish.
- [ ] Rollback plan: revert commit to restore prior content; `dist/` is regenerable from `build.py` + `content/`.

**Estimated effort:** Phase 1–2: ~1–2 days for a single engineer; Phase 3–4: ~0.5 day. No backend provisioning required for the recommended Decap path.

## 10. Public Interface Preservation Guarantee

The following are explicitly **out of scope for change** in this integration:
- `dist/style.css` — all styles, variables, media queries, reduced-motion handling.
- `dist/motion.js` — nav toggle, Escape handling, IntersectionObserver reveals, hero parallax.
- HTML structure, class names, ARIA attributes, skip link, footer, header/brand.
- Route URLs (`/`, `/work/`, `/work/<slug>/`, `/experience/`, `/about/`, `/contact/`).
- Animations, transitions, and responsive breakpoints.

The CMS layer only supplies **data** (text, images, links) to `build.py`, which emits the same HTML the public already consumes.
