# Secure Owner Provisioning — Portfolio Studio

## Model: Single Administrator, No Public Signup

Portfolio Studio has exactly one administrator. There is **no public registration**, **no invite flow**, and **no self-service signup**. The owner is provisioned once, out of band, by a trusted operator using the `owner` CLI against a disposable or production database.

### Security properties enforced

| Control | Implementation |
|---|---|
| Single owner | `provision()` rejects if an administrator already exists |
| Password | bcrypt(12 rounds), 12–72 UTF-8 bytes |
| MFA | TOTP (Base32 seed, 32–64 chars), encrypted at rest (AES-256-GCM) |
| Backup codes | 8 single-use codes, SHA-256 hashed, stored in `BackupCode` |
| Session | HTTP-only, Secure, SameSite=Lax cookie; server-side PostgreSQL store |
| MFA enforcement | `requireAdmin` requires `mfaVerified === true` and matching `sessionVersion` |
| Audit logging | Every auth, CRUD, and security action logged to `SecurityEvent` |
| CSRF | Double-submit token via `X-CSRF-Token` header on all state-changing requests |
| Rate limiting | Per-endpoint and shared owner budget (express-rate-limit) |

## Provisioning flow

Run from a **trusted operator shell** (not a CI pipeline, not a preview environment). The operator machine must be physically or VPN-secured.

### 1. Prepare environment variables

Set temporary variables only for the duration of the command. Do **not** commit them.

```bash
export OWNER_EMAIL="admin@example.com"
export OWNER_PASSWORD="<12-72 char password, generated by a password manager>"
export OWNER_TOTP_SEED="<32-64 char uppercase Base32, e.g. JBSWY3DPEHPK3PXP>"
```

- `OWNER_TOTP_SEED`: generate a new cryptographically random Base32 string. Enter it into the owner's authenticator app **before** provisioning so the first code is valid immediately.
- Do not reuse an existing TOTP seed.

### 2. Run the provision command

```bash
npm run owner -- provision /private/out/backup-codes.json
```

- `provision()` creates the administrator, stores the hashed password, creates the `MfaSecret` (encrypted TOTP seed, `enabled: true`), and generates 8 single-use backup codes.
- Output is written to a new file with mode `0600` (owner read/write only). The file must **not already exist** (`wx` flag).
- The file contains the 8 raw backup codes. Save them **offline** (e.g., printed or in a password manager). Never commit them.
- After success, unset the environment variables:

```bash
unset OWNER_EMAIL OWNER_PASSWORD OWNER_TOTP_SEED
```

### 3. Second factor setup

The owner opens their authenticator app and enters the TOTP seed. The first generated 6-digit code must be valid at first login. The server stores only the AES-256-GCM ciphertext of the seed; the plaintext seed is never persisted after provisioning.

### 4. First login

1. Client GETs `/api/admin/auth/csrf-token` (sets the `connect.sid` cookie and returns a CSRF token).
2. Client POSTs `/api/admin/auth/login` with `{email, password}` and `X-CSRF-Token`. Returns `202 { mfaRequired: true, csrfToken }`.
3. Client POSTs `/api/admin/auth/login/mfa` with `{token: <6-digit TOTP>}` and the rotated `X-CSRF-Token`. Returns `200 { ok: true, csrfToken }`.
4. The session is now `mfaVerified` and authorized for CMS writes.

### 5. Backup codes (single-use recovery)

If the owner loses access to their authenticator:

1. Complete the password step at `/api/admin/auth/login` (returns `202`).
2. POST `/api/admin/auth/login/backup-code` with `{code: <32-hex backup code>}` and the rotated CSRF token.
3. On success, the code is marked `used: true` and can never be used again.
4. Remaining unused backup codes stay valid.

## Recovery (password reset)

There is **no public password reset endpoint** and **no email delivery channel**. Recovery is operator-initiated:

```bash
npm run owner -- issue-reset /private/out/reset.json
```

This creates a single-use `PasswordResetToken` (SHA-256 hash, 15-minute expiry) and returns the raw token to the output file.

The operator delivers the token to the owner through a private, verified channel. The owner then POSTs `{token, password}` to `/api/admin/auth/recovery/verify` with a valid CSRF token. Success:
- Hashes the new password
- Increments `sessionVersion` (invalidating all existing sessions)
- Deletes all sessions for the administrator
- Marks the reset token as used
- Logs `RECOVERY_COMPLETE`

MFA remains mandatory after recovery.

## Operational rules

- **No public signup**: The API has no `/auth/register`, `/auth/invite`, or public user creation endpoint.
- **No credential printing**: The CLI writes secrets only to private files (mode `0600`) and never to stdout.
- **No credential reuse**: A second `provision()` call fails if an administrator already exists. Use `enroll-legacy` only for the single pre-existing owner immediately after a migration.
- **Backup codes offline**: Codes are shown once at provisioning. Lost codes cannot be reissued; use recovery instead.
- **TOTP seed never transmitted**: The seed is provided by the operator, never generated or returned by the API.
- **Rotate after compromise**: If the owner account is suspected compromised, run `issue-reset` to force a password change and session revocation.
